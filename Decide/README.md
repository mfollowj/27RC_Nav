# Decide —— 决策层：框架设计与可行性分析

> 版本：v0.1（**设计稿，不含实现**）　｜　日期：2026-10-31
> 规则依据：2027 ROBOCON《女娲补天》V1（策略原文在
> `/home/zx/ITEM/2027RC_mainRace_decision/01-目前最优决策.md`）
> 范围：**只做框架搭建与可行性分析**。本轮不写决策代码、不改 Nav。

## 一句话

决策层把"比赛策略"翻译成**带时限、可解释、可回放的任务序列**，在安全门控下
通过 Nav2 / 执行机构完成；它不负责定位、建图、避障和底层运动。

```
规则/策略 ──> 决策层（阶段 FSM + 决策点 + 任务计划 + 安全门控）
                       │
                       ├── NavigateToPose / ExecuteSkill ──> Nav2 / MCU / 执行机构
                       └── /decide/* ──> 日志 / 回放 / 监视
```

## 结论（先看这里）

| 结论 | 判断 |
| --- | --- |
| 框架本身 | **可行**：只依赖 rclpy / Nav2，无新增系统依赖；建议 3 个包 + 4 份 YAML |
| 现在就能落地的最小闭环（仿真） | **可行**：人工开赛 → 阶段/决策点 → 任务序列 → `NavigateToPose` → 安全门控 → 基础日志（回放下一步）；真机需先补地图/复验 |
| 仿真全流程（作业技能用 mock） | **有条件可行**：仿真图自由区约 6.5 m²，够验证"任务序列/异常处理"，不够验证全场 |
| 真机全流程（自动） | **当前不可行**：先验图自由区仅约 0.39 m²；无场地语义/计分输入；无取石/建塔/翻顶执行接口 |
| 全自动 180 s 比赛 | **不可行**（同上三条硬前置） |

三条硬前置（缺一不可）：

1. **全场先验图**：自由区覆盖所有元素作业点，重定位残差 p95 ≤ 0.15 m；
2. **输入源**：分差 Δ、对手可翻 L2 顶数 n、元素占用状态，至少有人工输入通道；
3. **执行接口**：至少一个作业技能（建 L1/L2、取放石、翻顶）可以被 action 调用。

> 这三条不解决，决策层做得再完整也只能"空跑"。因此本设计把
> **安全壳 + 任务调度 + 人工输入 + 日志** 作为第一阶段的可交付物（回放随策略层一起做），
> 把"全自动"明确列为后续里程碑，而不是本阶段的承诺。

## 与 Nav 的分工

| 能力 | 归属 | 说明 |
| --- | --- | --- |
| 雷达驱动 / LIO / 重定位 / TF | Nav | 决策层只消费，不改、不伪造 |
| 地图 / 代价地图 / 避障 | Nav | 决策层只读；目标合法性由 Nav2 和网关共同把关 |
| 比赛时钟 / 计分 / 元素状态 | Decide（+ 人工/裁判） | **当前最大缺口**，见 04 |
| 阶段判断 / 任务排序 / 时限 | Decide | 纯函数策略，可离线回放 |
| 作业动作（建塔/取放石/翻顶） | Decide 调 Skill，底层由执行机构实现 | **当前无接口**，见 04 |
| 安全否决 / 急停 / 单写者仲裁 | Decide | 默认拒绝，宁可不动 |

## 本轮不做什么

- 不写 `decide_core` / `decide_skills` 的实现代码；
- 不做场地元素识别（无相机、无训练数据、规则未冻结）；
- 不改 Nav 的 LIO / 重定位 / Nav2 参数；
- 不承诺"全自动打完整场"。

## 下一步（建议顺序）

1. **先把安全壳 + 单目标导航跑起来**（10~16 人日）：`TRACKING` 才允许发目标、177 s 冻结、全量日志；
2. **并行补两条前置**：全场先验图（Nav，最高优先级）、作业技能接口（机械/电控）；
3. **再上策略**：人工输入 Δ/n/元素状态，跑通 4 个分支；
4. **最后谈自适应**：有感知或裁判数据后，再把人工输入换成自动输入。

每一步的验收标准见 [04-可行性分析](04-可行性分析.md) 的"里程碑与验收"。
