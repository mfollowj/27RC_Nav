## 1. 结论先行

| 范围 | 内容 | 结论 | 主要依据 |
| --- | --- | --- | --- |
| S0 | 框架、接口、策略映射（本轮文档） | **完成** | 本文档集 |
| S1 | 安全壳 + 单目标导航 + 基础日志 | **可行，现在就能做（仿真）** | Nav2 仿真已验证；`/reloc_status` 可用；真机见 S4 |
| S2 | 任务序列 + 人工输入 Δ/n/元素状态（作业技能人工确认） | **仿真有条件可行；真机被地图卡住** | 仿真图自由区 6.47 m²，元素点需逐个确认可达；真机 0.39 m² |
| S3 | 仿真"整场"流程（技能 mock、故障注入） | **有条件可行** | 地图只覆盖局部；场地是近似场 |
| S4 | 真机单任务（导航到点 + 人工确认作业） | **有条件可行** | 需先重做全场图、复验 P2/P3 |
| S5 | 真机全自动 180 s 比赛 | **当前不可行** | 三条硬前置均未满足 |

三条硬前置：

1. **全场先验图**（Nav）：自由区覆盖所有元素作业点，重定位残差 p95 ≤ 0.15 m；
2. **输入源**（Decide + 裁判/人工）：Δ、n、元素占用至少有人工通道；
3. **执行接口**（机械/电控 + Decide）：至少一个作业技能可被 action 调用。

> 一句话：**决策层的"大脑"可以现在写，"手"和"眼睛"还没有。**
> 先把安全壳和任务调度做出来，能立刻降低"乱发目标/超时/违规"的风险；
> 全自动比赛必须等三条前置，不能靠决策层单方面补。

## 3. 关键缺口（带数字）

### 3.1 真机先验图几乎不可用

`Nav/real/maps/prior_costmap.meta.json` 与 `prior_costmap.pgm`：

| 指标 | 数值 |
| --- | ---: |
| 地图尺寸 | 6.05 m × 6.05 m（121 × 121 格，0.05 m） |
| 自由格 | 157 格 = **0.39 m²**（1.07%） |
| 占据格 | 2228 格 = 5.57 m²（15.2%） |
| 未知格 | 12256 格 = **30.6 m²**（83.7%） |
| 先验点云 | 21886 点；轨迹 7 点 |
| `imu_height` | **0.003 m（错误，应为 0.30）** |

`imu_height` 写成 0.003 m 会让 2D 切片把地面高度算错，**这也是自由区只有 0.39 m² 的直接原因之一**。

**影响**：Nav2 的静态层 `track_unknown_space: true`，真机 `planner_server` 又设了
`allow_unknown: true`（`Nav/real/config/nav2_real.yaml`）。两者叠加，规划器**可能穿过未知区**；
而自由区只有 0.39 m²，任何跨元素的转场都会失败或走进未知。
`inflation_radius: 0.75 m` 还会把可规划区域进一步压缩，实际可走的范围比 0.39 m² 更小。
**这不是决策层能修的**，必须先按 `Docs/项目当前情况.md` 的问题 #1 重做全场图。

### 3.2 仿真地图也只覆盖局部

`Nav/ros2_ws/install/rc_field_nav/share/rc_field_nav/maps/field_costmap.meta.json` / `field_costmap.pgm`：

| 指标 | 数值 |
| --- | ---: |
| 地图尺寸 | 7.4 m × 7.2 m（148 × 144 格） |
| 自由格 | 2587 格 = **6.47 m²**（12.1%） |
| 未知格 | 18031 格 = 45.1 m²（84.6%） |

**影响**：够验证"任务序列/状态机/异常处理"，**不够**验证"全场四个阶段的任务编排"。
仿真里能到的元素点，必须逐个确认在自由区内，否则 S3 的"整场"只是名义上的。

### 3.3 没有场地语义层

- `map3d_to_costmap.py` 只输出占据/地形/可通行性，没有元素 ID、归属、塔顶状态；
- 全仓库搜索没有 tower/stone/element 的语义实现（只有 `mcu_bridge` 的注释里出现"语义"二字）；
- 无相机（`livo_mid360.yaml` 的 `img_en: 0`），LiDAR-only 做元素识别的成本/可靠性都不适合本阶段。

**影响**：元素坐标只能靠 `field.yaml` 人工标定；占用/翻顶只能靠人工输入。
这能支持"固定剧本"，不支持"自适应比赛"。

### 3.4 没有计分/裁判输入

- 仓库里没有裁判盒/计分协议的任何代码或话题；
- 策略需要的 `Δ`、`n` 没有来源；
- 规则版本 V1，且原文自己标注"V2 发布后全线重算"。

**影响**：终局四分支无法自动判断；只能人工输入，或退化为"固定剧本"。

### 3.5 没有作业执行接口

| 技能 | 现状 |
| --- | --- |
| `build_l1` / `build_l2` | 无 action/service/串口命令 |
| `pick_stone` / `place_stone` | 同上 |
| `flip_top` | 同上 |

`mcu_bridge` 的串口协议只有 `x/y/yaw` 位置帧，**没有夹持/升降/翻转命令**；
`/cmd_vel` 也只能驱动底盘。决策层能"走到位"，但不能"干活"。

另外，真机 `nav2` 后端还缺一条**已验证的 `/cmd_vel` 通路**：Nav2 发 `/cmd_vel`，
真机底盘当前吃的是 MCU 串口位置帧。要么底盘驱动直接订阅 `/cmd_vel`，要么用
`mcu_bridge enable_velocity:=true` 把 `/cmd_vel` 转成速度帧；两条都未在真机验证。
这属于"决策层依赖"而不是"决策层能修"的问题，排期时要单独列。

### 3.6 全局位姿精度与对接精度不匹配

- 重定位残差实测 `diff=0.19 m / 1.9°`，会话最大 `0.23 m / 3.0°`；
- Nav2 目标容差 `0.15 m / 0.20 rad`；
- 元素作业位若要求 ≤5 cm（`work_tol`），**全局位姿误差已经大于它**。

**影响**：对接/建塔不能只靠"导航到 work 位"，必须有精对齐（视觉/激光伺服/机械导向）
或机械容差设计。决策层必须把 `navigate` 和 `align` 分开，不能假装 Nav2 能到 3 cm。

### 3.7 多级地形未验收

- 仿真场地有 L1（6×6，高 0.602 m）、L2（3×3，高 0.901 m）、坡道（约 9.7°）、台阶；
- Nav2 只加载 trinary 障碍图（`prior_costmap.pgm`），`*_cost.pgm` 的地形代价**没有进 Nav2**；
- 现有仿真导航只验证了 1 个自由区目标点，日志没有记录 z 变化或坡度事件。

**影响**："上 L1 高台建塔"是否可达、是否安全，**没有证据**。必须补一条显式的
"从地面经坡道到 L1 作业位"的验收用例，否则不能把 L2 任务写进计划。

### 3.8 策略时间常数未标定（含开局 t0）

`t1/t2/tM/tF` 在原文里明确"待实测 ≥10 次"。没有它们：

- 无法判断"48 s 内两座 L1"是否可行；
- 无法判断"150–177 s 翻两个顶"是否可行；
- 决策层的"时间预算"是空的。

按 [03](03_strategy_mapping.md) 的 20% 余量口径，完整计划要求
`t1≤18.75、t2≤28.75、tM≤22.5、tF≤10`（两次翻顶）。这是一组**很紧**的数，
必须实测后才能确认策略是否需要缩减。注意 `t1≤18.75` 是按"开局转场 `t0=0`"反算的；
若 `t0=5 s`，则 `t1≤16.67`。`t0` 也必须实测。

### 3.9 真机 P2/P3 未复验

`Docs/项目当前情况.md` 明确：P2/P3 改了 `env.sh`、共用 yaml、launch 默认路径，
真机还没上车复验。任何"真机决策层"的排期都必须先包含这一步。

## 5. 逐项可行性判断

| 项 | 判断 | 条件 / 说明 |
| --- | --- | --- |
| 框架与接口设计 | **可行** | 只依赖现有 ROS 2 / Nav2；本文档可直接落地 |
| 安全壳（仅门控/冻结/急停，不含导航） | **可行** | `/reloc_status` 已可用；约 6~10 人日（M-D1 + M-D2） |
| 阶段 FSM + 决策点 | **可行** | 纯逻辑，单测覆盖边界即可 |
| 任务序列 + Nav2 | **仿真可行** | 需要地图自由区覆盖目标；真机受 3.1 限制 |
| 人工输入 Δ/n/元素状态 | **可行** | `manual_console`；缺点是有延迟和误操作，需要确认流程 |
| 自动元素识别 | **本阶段不可行** | 无相机、无数据、规则未冻结；不建议用 LiDAR 硬做 |
| 自动计分/裁判 | **不可行** | 无协议；等规则/裁判盒 |
| 作业技能（建/取/放/翻） | **不可行** | 无执行接口；需机械/电控先定协议 |
| 多级地形（L1/L2/坡道） | **未验证** | 需补验收用例；2D Nav2 不建模坡度 |
| 精对齐（≤5 cm） | **有条件可行** | 需要额外后端（位置伺服/视觉/机械导向），不能只靠全局位姿 |
| 时间预算 / 策略可行性 | **有条件** | 依赖 t0/t1/t2/tM/tF 实测；未标定则 fail-closed |
| 回放 / 复盘 | **可行** | 纯函数策略 + JSONL；对调试价值高 |
| 仿真整场演练 | **有条件** | 地图 6.47 m²、场地近似、无对手模型 |
| 真机全自动比赛 | **不可行** | 3.1 + 3.3/3.4 + 3.5 三条硬前置 |

## 8. 测试与验收

### 8.1 单元测试（不依赖 ROS）

| 用例 | 期望 |
| --- | --- |
| `/reloc_status` 四种 mode + 缺字段 + 乱序 | 解析正确；未知 key 忽略；失败不沿用旧 mode |
| 门控阈值边界 | `applied=0`、`diff=0.5`、age=1.0 的边界行为明确 |
| 时钟暂停/跳变/回退 | 暂停冻结阶段；跳变>2 s 判无效 |
| DP 时间边界 | 47.9/48.1、77.9/78.1、107.9/108.1、149.9/150.1、164.9/165.1、176.9/177.1 |
| `k = ceil(Δ/160)` | Δ=0/1/159/160/161/255/320 |
| 时间预算 | `t0+2×t1×1.2+3≤48` 等公式；超预算不选该任务 |
| 分支规则 | 四分支 + 输入无效的保守分支 |
| 配置校验 | 重复 ID、越界位姿、版本不匹配、哈希不匹配 |
| 符号约定 | `Δ=opp−own`；领先/落后不写反 |
| 回放确定性 | 同一 JSONL 两次 `plan` 完全一致 |

| 目标不可达 | 目标在未知区 | G5 拒绝；元素 `UNREACHABLE`；不反复重试 |
| Nav2 掉线 | kill `bt_navigator` | 拒绝导航任务；不崩；恢复后继续 |
| 时间临界 | 5× 时钟 | 177 冻结；179 前所有技能取消 |
| 人工接管 | `/decide/set_manual` | 立即 PAUSED；恢复后重评估 |

## 11. 建议

1. **先做 S1（安全壳 + 单目标导航）**：这是唯一"现在就能在仿真上跑、且一定有用"的部分。
   它把"未定位乱发目标""177 s 还在动""出了问题没日志"三个风险直接消掉。
2. **同时补两条前置**：
   - Nav：重做全场先验图（`real_save_map.sh --imu-height 0.30`），这是最高优先级；
   - 机械/电控：确定作业技能的 action 协议（可直接用本文 `ExecuteSkill`）。
3. **S2 在仿真里跑通**：人工输入 Δ/n/元素状态，验证 4 个分支和异常；
   不要把仿真里调出来的"战术参数"当真机结论。
4. **S5 之前不要承诺"全自动"**：三条硬前置没有捷径；决策层无法替代地图、感知和执行机构。
5. **规则 V2 发布后**：只改 `policy.yaml` 和 `field.yaml`，代码不动；
   如果必须改代码，说明契约设计有问题，先修契约。
