# 仓库维护与更新

一次改动同时交代三件事：改了什么、运行者需要怎么用、用什么结果确认。源码、参数和对应文档尽量随同一个提交或 PR 更新。

## 开始修改

从 [源码与配置索引](source_index.md) 找到受影响的入口与包，先运行当前流程并记下结果，再修改。默认保留现有包名与目录；需要搬文件时，一起更新 launch 路径、安装规则、脚本、资源引用和文档。

使用普通 Git 分支保存过程。例如：

```bash
git status --short
git switch -c codex/update-navigation
# 编辑后检查差异，按本次修改选文件暂存
git diff
git add README.md docs/source_index.md
git commit -m "docs: clarify navigation entrypoints"
```

提交前用 `git diff --cached` 确认包含需要的改动。测试数据、生成产物或无关联调文件按各自用途保存；已有本地改动保留在原来的任务范围内。

## 常见修改的更新步骤

| 改动 | 需要同步 | 适合的验证 |
| --- | --- | --- |
| 文档、路径或启动示例 | 根 README／docs 索引及所引用文件 | 链接与路径存在，示例参数能被对应入口识别 |
| launch／YAML／业务脚本 | 对应包安装规则与使用说明 | 构建受影响包，展开参数，再实际运行受影响链路 |
| C++、ROS 消息或插件 | `CMakeLists.txt`／`package.xml` 依赖和调用方 | 编译并运行相应节点或场景 |
| 机器人尺寸、轮径、外参 | 机器人模型、底盘参数、Nav2 footprint／TF | 静态模型检查，低速位移／转向与点云观察 |
| 地图或场地 | [生成源、先验图、栅格图及使用说明](maps.md) | 查看场地与坐标，再做定位和短目标导航 |
| 串口协议或坐标换算 | 电控约定、YAML、编解码与包 README | 现有帧测试、PTY／dry-run，再真机联调 |
| 第三方依赖 | 来源、许可证、本地补丁说明、构建入口 | 重建该依赖及使用它的本项目包，运行相应链路 |
| Decide 实现 | 对应设计、接口和可运行入口 | 先验证单任务及导航取消／失败行为，再组合比赛流程 |

检查范围随实际改动选择。已有单元测试用于检查实现，运行和测量用于确认机器人行为；文档检查不能代替导航与传感器链路的执行。

## 构建与重启

全量构建使用 `./build.sh`；依赖已就绪时使用 `./build.sh nav`。默认采用普通安装，避免目标机 setuptools 对 editable 安装的兼容差异。单组件入口仍保留，例如：

```bash
./third_party/build_deps.sh fast_livo
./build.sh nav
source env.sh
```

仅配置真机环境的小电脑，首次使用 `JOBS=1 ./build.sh robot`；依赖已就绪后，增量构建使用 `./build.sh nav --packages-select relocalization mcu_bridge`，避免选择需要 Classic 的仿真包。

仅修改某个项目包时，可从新终端加载环境后按包构建：

```bash
source env.sh
colcon build --packages-select relocalization
```

新增依赖或修改对外接口后，连同使用它的包重建。普通安装下，修改 launch／YAML／Python 文件也应构建并重启对应入口，确保运行的已安装文件与源码一致；使用符号链接安装时按实际链接与包工具链处理。

`mcu_bridge` 的旧机器人部署记录包含 setuptools 不支持 editable 安装的情况，普通 `colcon build --packages-select mcu_bridge` 可避免该路径。不要把某台机器的编译耗时写成所有机器的固定耗时。

## 参数与场地更新

文件按 [命名与迁移](naming.md) 的职责与 snake_case 规则维护。根目录是工作区，项目源码放 `src/`，真机资源放 `robot/`，共用参数放 `config/`，场地源放 `simulation/`；第三方目录保留上游名称。

先尝试通过已有 launch 参数选择地图、参数文件、出生点或场地。长期采用的默认配置再写回源码，并更新 [脚本目录](scripts.md)。配置的作用范围要明确：共用 LIO、真机 Nav2、仿真 Nav2、驱动网络和串口协议各有对应文件。

生成资源修改生成源，再用仓库现有命令生成。地图更新须配对相同坐标系下的 PCD 与栅格；场地版本、机器人外参、任务点和导航参数的对应关系写入 [地图文档](maps.md)。

`third_party/` 保存第三方源码与本地修改。升级时先对比上游变更与本地补丁，保留必须的本地行为；修改 `third_party/fast_livo` 后同步 [补丁说明](../robot/patches/README.md)，再验证建图、先验跟踪和恢复中的相关场景。原有保护措施保留到有明确替代实现并验证后再调整。

## 推送与 PR

本地提交完成后推送工作分支，再向目标分支建立 PR：

```bash
git push -u origin codex/update-navigation
```

PR 描述写清具体问题与结果、主要涉及路径、使用方式变化、实际执行的验证及剩余工作。地图 PR 附来源与预览，导航参数 PR 附目标结果和定位表现，协议 PR 附帧样例与电控联调结果。尚未执行的真机验证写在相关说明里一次，方便后续接手。

Git 提交与分支记录变更；明确发布版本时再更新对应包版本号和发布说明。日常改动沿用现有测试与工具，不额外建立冻结配置、baseline 或审批门禁。

## 更新机器人

优先在目标机获取同一分支源码、查看 Git 状态，再在目标机构建。换机器或 CPU 架构时重建依赖和项目包；运行目录仍使用仓库根脚本。

`tools/deploy_mcu_bridge.sh` 是现有的单包同步工具，使用 rsync 同步目标包并在远端构建，默认机器人地址和路径见脚本。它保留旧机器人工作区的 prefix chain；确认目标机配置并查看脚本后再使用。完整仓库部署按 [上手与部署](getting_started.md) 进行。

运行前停止原入口；如果由已安装的用户服务管理，先停服务再手工联调。检查串口和雷达由当前工作流使用，再启动新入口。更新后记录实际版本、机器、场地／地图、命令、结果与关键日志。

## 文档怎么保持可读

- 新的常用入口加入 [脚本目录](scripts.md)，参数或路径变化更新 [源码索引](source_index.md)。
- 代码已实现的行为、实测结果和未来计划分别写清，`Decide` 的计划结构在代码落地后再加入运行步骤。
- 当前状态更新 [项目当前情况](status.md)；历史测量保留日期、条件和结果，旧机器路径放在历史记录里。
- 新增资料从 [docs/README](README.md) 链接，内容尽量放在对应职责的文档中，避免多个 README 重复维护同一份参数表。
